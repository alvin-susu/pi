# AgentHarness 生命周期

`AgentHarness` 是位于底层智能体循环之上的编排层，负责会话持久化、运行时配置、资源解析、操作锁定，以及面向扩展的变更语义。

本文介绍当前的设计方向和已经实现的行为。部分扩展/会话门面细节尚处于规划阶段，文中会明确指出。

## 生命周期的最终目标

运行框架监听器和钩子应能通过闭包引用 `AgentHarness` 实例，并在文档允许的任何事件中调用运行框架的公开 API。这些调用不能破坏正在执行的轮次快照、打乱已持久化对话条目的顺序、丢失待处理写入、导致收尾过程死锁，也不能让运行框架停留在错误阶段。

预期规则如下：

- 忙碌时仍拒绝结构性操作
- 在文档规定的轮次安全点接受队列操作
- 运行时配置 setter 更新后续快照，不修改当前服务提供商请求
- 忙碌期间发起的会话写入进入持久化队列，并按确定性顺序刷新
- getter 返回最新的运行框架配置，而不是正在执行的快照
- 目前监听器/钩子不会收到门面；如果它们通过闭包引用原始运行框架，并在运行期间调用 `waitForIdle()` 等收尾 API，可能导致死锁。未来的门面应改为公开 `runWhenIdle()`。

`AssistantMessageStream` 已将服务提供商的传输流（例如 SSE 或 WebSocket 读取）与下游事件消费解耦。因此，运行框架可以等待监听器、扩展钩子、持久化和保存点工作完成，而不会阻塞服务提供商的传输读取器，也无需重新引入临时拼凑的事件队列。生命周期代码应优先在运行框架边界上显式等待各步骤按序完成，不应以“触发后不管”的方式处理钩子/事件收尾。

最后还应进行一轮生命周期加固，通过覆盖面广泛的监听器/钩子重入测试套件来验证这些保证。

## 错误处理

当前的职责划分如下：

- 对于可预期且必须收敛为非抛出式错误的底层能力和辅助函数，使用 `Result<TValue, TError>`，例如 `ExecutionEnv`、文件系统/shell 操作、shell 输出捕获、资源加载和上下文压缩辅助函数
- `Session`、`AgentHarness` 等高层变更/编排 API 通过 Promise 拒绝或抛出错误，而不是返回容易被忽略的裸结果
- 在可行的情况下，将 `AgentHarness` 公开 API 的失败统一为 `AgentHarnessError`；子系统错误保留为 `cause`

运行框架事件观察的是已提交状态。只要可行，公开变更方法会先校验必需输入并确认能够持久化，再提交变更，随后等待通知完成。如果钩子或订阅者在提交后失败，状态变更不会回滚，公开方法会以代码为 `"hook"` 的 `AgentHarnessError` 拒绝。

## 状态模型

运行框架将状态分为四类。

### 运行框架配置

运行框架配置是应用或扩展所设置的最新运行时配置：

- 模型
- 思考级别
- 工具
- 已启用工具名称
- 工具上下文来源
- 资源
- 流式传输选项
- 系统提示词或系统提示词提供器

getter 返回运行框架配置，不会返回正在执行的服务提供商请求所使用的快照。

setter 会立即更新运行框架配置，即使某一轮对话仍在执行。变更影响下一轮快照，不影响当前正在执行的服务提供商请求。

`setResources()` 接受具体资源。每次调用都会发出 `resources_update`，其中包含浅拷贝后的当前资源和先前资源。应用负责从磁盘或其他来源加载/重新加载资源，并应使用新值调用 `setResources()`。

`getResources()` 返回浅拷贝后的当前资源。它读取的是实时配置，而不是上一轮快照。

### 轮次快照

轮次快照是某一轮 LLM 交互所使用的具体状态，由 `createTurnState()` 创建，包含：

- 已持久化的会话消息
- 解析后的资源
- 解析后的系统提示词
- 模型
- 思考级别
- 全部工具
- 已启用工具
- 解析后的工具上下文
- 流式传输选项
- 派生的会话 ID

静态选项值会被直接使用。每次调用 `createTurnState()` 时，系统提示词提供器回调只执行一次。该轮的所有逻辑都使用同一个快照。

创建快照时会浅拷贝资源数组，但不会深拷贝单个技能和提示词模板对象。

`toolContext` 由应用定义；如果配置的工具要求上下文不能为 `undefined`，则必须提供该值。静态值会被复用，而无参数的同步或异步提供器会为每个轮次快照解析一次。运行框架工具执行时会收到解析后的值。每个工具可以通过结构类型只要求自身会使用的上下文字段。

创建快照时会浅拷贝流式传输选项。`headers` 和 `metadata` 映射也会被浅拷贝，但其值不会深拷贝。每次服务提供商请求都会重新解析 `getApiKeyAndHeaders()` 返回的凭据，以便刷新即将过期的 token；不过，配置的流式传输选项和派生会话 ID 仍来自当前轮次快照。

### 内置工具

该包导出 `createReadTool()`、`createWriteTool()`、`createEditTool()` 和 `createBashTool()`。它们只通过工具上下文提供的 `ExecutionEnv` 执行文件系统和 shell 操作。每个工具在结构上都要求共享的 `ExecutionToolContext`，其中包含 `env: ExecutionEnv`；应用可以提供额外字段。`createReadTool()` 接受可选的图像处理器，由宿主完成格式转换和尺寸调整，从而避免让 agent 包依赖图像处理库。`createBashTool()` 接受异步 `prepare` 钩子，该钩子可以利用当前工具上下文修改命令、工作目录、环境变量和环境继承策略。

### 会话

会话只包含已持久化的条目。读取会话时返回已持久化状态，不包含已排队的写入。

`Session.buildContextEntries()` 返回用于构建模型上下文、且已考虑上下文压缩的条目序列。`Session.buildContext()` 从完整的当前分支中派生运行时状态，再将这些上下文条目投影为 `AgentMessage[]`。默认情况下，模型上下文会忽略自定义条目；应用可以向 `Session` 构造函数或 `buildContext()` 传入 `entryProjectors`，将选定的自定义条目投影为消息。应用还可以传入层叠的 `entryTransforms`：这些转换会在默认的上下文压缩转换之后运行，并在投影前筛选上下文条目或调整其顺序。

会话存储实现必须将叶节点变更持久化为 `leaf` 条目。`setLeafId()` 不只是更新内存中的游标；它会追加一个持久化条目，其 `targetId` 是当前树的叶节点，根节点则为 `null`。重新打开存储时，必须根据最近一个影响叶节点的持久化条目重建当前叶节点。

### 待处理会话写入

操作期间请求的会话写入会进入待处理会话写入队列。待处理写入采用不含生成字段（`id`、`parentId`、`timestamp`）的会话条目结构。

待处理会话写入始终会被持久化，并在保存点、操作收尾和失败清理阶段刷新。

公开的待处理写入/会话门面 API 已纳入规划，但尚未实现。

## 操作阶段

运行框架具有显式的阶段：

```ts
type AgentHarnessPhase = "idle" | "turn" | "compaction" | "branch_summary" | "retry";
```

结构性操作要求 `phase === "idle"`，并会在第一个 `await` 之前同步设置阶段：

- `prompt`
- `skill`
- `promptFromTemplate`
- `compact`
- `navigateTree`

运行框架非空闲时，如果启动另一个结构性操作，操作会以代码为 `"busy"` 的 `AgentHarnessError` 拒绝。

在适当情况下，一轮对话期间允许执行以下操作：

- `steer`
- `followUp`
- `nextTurn`
- `abort`
- 运行时配置 setter

阶段/收尾语义仍是暂定方案，需要进行完整的生命周期审查。

## 轮次执行

`prompt`、`skill` 和 `promptFromTemplate` 遵循相同流程：

1. 断言当前为空闲状态，并将阶段设为 `"turn"`。
2. 使用 `createTurnState()` 创建轮次快照。
3. 从该快照派生调用文本。
4. 使用 `executeTurn()` 执行该轮对话。

`skill` 和 `promptFromTemplate` 从传给该轮对话的同一个快照中解析资源，不会另行解析。

`steer`、`followUp` 和 `nextTurn` 接受文本与可选图像，并在内部创建用户消息。下一次由用户发起对话时，`nextTurn` 消息会插入到新的用户消息之前。

队列模式采用实时值，不会纳入轮次快照：

- `getSteeringMode()` / `setSteeringMode()`
- `getFollowUpMode()` / `setFollowUpMode()`

运行期间更改队列模式会影响下一次队列取出操作。队列只在安全点取出消息。

## 保存点

助手轮次及其工具结果消息全部完成后，会到达一个保存点。

在保存点，运行框架会：

1. 在该轮智能体发出的消息之后，刷新待处理会话写入
2. 如果底层循环可能继续，则创建新的轮次快照
3. 在下一次服务提供商请求之前，应用新的上下文、模型、思考级别、流式传输选项和会话 ID 状态

这样，一轮对话期间对模型、思考级别、工具、资源、流式传输选项和系统提示词所作的变更，就能影响同一次运行中的下一轮对话，同时绝不会修改正在执行的服务提供商请求。由于 `AssistantMessageStream` 已将服务提供商的传输读取解耦，可以直接等待保存点工作和钩子收尾完成，以保持对话记录/会话顺序的确定性。保存点不会重新创建循环回调。

底层循环会在服务提供商边界将运行框架的 `ThinkingLevel` 转换为服务提供商的 `reasoning`：

- `"off"` → `undefined`
- 其他思考级别原样传递

在 `agent_end` 时无需刷新状态，只需刷新剩余的待处理会话写入并清除操作阶段。`settled` 事件的确切触发时机仍在审查中。

如果系统提示词回调在启动 `prompt`、`skill` 或 `promptFromTemplate` 时抛出错误，操作会以 `AgentHarnessError` 拒绝，运行框架则恢复为空闲状态。如果错误来自 `prepareNextTurn` 创建的保存点快照，底层智能体运行会记录一条助手错误消息。

## 钩子与事件

目标钩子系统详见 [hooks.md](./hooks-zh.md)。

概要：

- `AgentHarness` 发出类型化的钩子事件，并使用类型化的结果。
- 单一钩子实现负责注册、清理、来源信息和结果归并器。
- 观察钩子和变更钩子共用按事件区分的 `on()` API；事件的结果类型决定处理器能否返回结果。
- 通过类型化的归并器表归并会产生结果的事件；应用专用钩子只为应用专用且会产生结果的事件增加归并器。
- 钩子注册来源作为注册项的旁路元数据保存。资源和工具的来源信息则属于应用专用的具体值类型。
- 钩子上下文应是由门面组成的普通对象，而不是原始内部对象或延迟绑定的 getter 迷宫。

事件载荷描述正在发生的事情；运行框架 getter 描述供未来快照使用的最新配置。只要可行，就应按照生命周期顺序等待钩子和监听器完成。`AssistantMessageStream` 已在运行框架下层处理传输背压，因此运行框架不需要仅为保持 SSE 或 WebSocket 持续读取而另设异步事件队列。

### 摘要重试事件

为运行框架配置重试策略后，如果生成上下文压缩摘要或分支摘要的请求遇到服务提供商瞬时错误，就会发出重试生命周期事件：

- `retry_scheduled`：已经安排重试。包含 `operation: "compaction" | "branch_summary"`、`attempt`、`maxAttempts`、`delayMs` 和 `errorMessage`。
- `retry_attempt_start`：退避延迟已经结束，重试的摘要请求即将开始。包含 `operation`。
- `retry_finished`：重试循环因成功、次数耗尽或中止而结束。包含 `operation`。

这些都是观察事件，不接受钩子结果。

## 规划中的会话门面

扩展最终应通过运行框架作用域内的 `HarnessSession` 门面与会话交互，而不是直接操作原始会话。该门面应封装内部会话，并强制执行运行框架的待处理写入顺序语义。门面实现后，钩子和事件监听器接收的上下文可以公开完整的 `AgentHarness` 及会话门面，同时不允许直接发起无序的原始会话写入。

规划中的读取语义：

- 将读取委托给已持久化的会话状态
- 读取结果不包含已排队的待处理写入

规划中的写入语义：

- 空闲：立即持久化
- 忙碌：作为待处理会话写入入队

规划中的诊断 API 可以显式公开待处理写入：

```ts
getPendingWrites(): readonly PendingSessionWrite[]
```

智能体发出的消息会在 `message_end` 时持久化，以保持对话记录的顺序。在保存点，待处理的扩展/会话写入会在这些消息之后刷新。

## 中止

允许在一轮对话期间中止。中止会终止底层运行，并清空引导消息/后续消息队列。

中止不会清除 `nextTurn` 消息。通过 `nextTurn()` 排队的消息会在中止后保留，并在下一次用户发起的轮次中插入到用户消息之前。

中止不会丢弃待处理会话写入。如果后续到达保存点，则会在该保存点刷新；否则会在 `agent_end` 或操作失败清理阶段刷新。

中止屏障语义仍需审查。

## 上下文压缩与树导航

上下文压缩和树导航属于会话结构变更。

它们只能在空闲时执行，不会进入队列，并且只操作已持久化的会话状态。下一次提示会创建全新的轮次快照。

生成分支摘要是树导航操作的一部分。

`AgentHarness` 尚未实现自动压缩和重试决策点。

## 测试组织

运行框架测试应按功能领域划分，避免不断扩充成一个包罗万象的大文件。

当前结构：

- `packages/agent/test/harness/agent-harness.test.ts`：核心生命周期和公开 API 行为。
- `packages/agent/test/harness/agent-harness-stream.test.ts`：流式传输选项和服务提供商钩子语义。

建议采用的未来结构：

- `agent-harness-resources.test.ts`：资源快照/加载语义。
- `agent-harness-tools.test.ts`：工具注册表 getter、已启用工具语义和更新事件。
- `agent-harness-lifecycle.test.ts`：阶段/保存点/收尾/重入行为。

使用 `pi-ai` 的模拟服务提供商（`registerFauxProvider`、`fauxAssistantMessage`）进行具有确定性的运行框架/服务提供商测试。模拟响应工厂可以检查 `StreamOptions`、调用 `options.onPayload`，并返回预先编排的助手消息，不需要真实的服务提供商 API 或网络访问。

运行框架覆盖率与包的默认测试运行分开配置：

```bash
npm run test:harness
npm run coverage:harness
```

`coverage:harness` 运行 `test/harness/**/*.test.ts`，并将 `src/harness/**/*.ts` 以及测试直接执行的非运行框架运行时文件（`src/agent.ts` 和 `src/agent-loop.ts`）的覆盖率报告写入 `coverage/harness`。`src/types.ts` 等仅包含类型的依赖没有实际的运行时覆盖率意义，因此不会纳入统计。
