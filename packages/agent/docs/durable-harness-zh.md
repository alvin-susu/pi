# 可持久化 AgentHarness 与会话设计

可持久化 AgentHarness / 会话设计笔记。

## 问题界定

仅靠 `AgentHarness` 自身无法真正实现完全持久化，因为一些重要依赖是在运行时由宿主应用提供的 JavaScript 对象：

- 工具实现
- 模型/身份验证服务提供商
- 扩展和钩子处理器
- 资源加载器
- 系统提示词回调/修改器

工具注册表属于运行时依赖。运行框架应持久化可序列化的工具配置，例如已启用工具的名称，但不应持久化具体的工具实现。

更切实际的目标是实现一个半持久化运行框架：

- 会话是可持久化、仅追加的状态树
- 运行框架将自身负责的状态持久化为会话条目
- 恢复会话时，由宿主应用重新创建兼容但无法持久化的依赖
- 恢复过程从持久化边界重新开始，而不是接续正在传输的服务提供商流

## 由会话承载持久化状态

应将会话视为智能体全部持久化状态的载体，而不只是对话记录。

现有的会话状态已经包含运行框架状态：

- 模型变更
- 思考级别变更
- 已启用工具变更
- 叶节点条目
- 标签
- 上下文压缩和分支摘要
- 自定义消息和自定义条目

因此，应继续使用单一的持久化会话日志，而不是额外增加运行框架的旁路文件。大型二进制对象仍可存放在旁路文件中，但会话条目必须继续作为事实来源的引用。

## 恢复时应用必须提供的内容

应用必须重新创建兼容的运行时依赖：

- 模型注册表/模型对象
- 工具注册表
- 扩展集合、版本和顺序
- 资源加载器
- 系统提示词提供器/钩子
- 身份验证服务提供商
- 应用专用钩子

如果这些依赖提供了稳定的 ID、版本或哈希值，运行框架可以进行校验，但无法自行序列化这些依赖。

## 运行时配置与恢复

构造函数选项仍是显式的运行时配置，不会读取会话状态。如果在构造函数中隐式执行异步恢复，失败处理将变得含糊不清。

未来应由异步构建器/工厂负责持久化恢复：

```ts
const harness = await AgentHarness.builder()
  .env(env)
  .session(session)
  .model(defaultModel)
  .tools(runtimeTools)
  .defaultActiveTools(["read", "edit"])
  .restore({ missingActiveTools: "fail" });
```

`restore()` 应读取当前分支，将持久化条目归并为运行框架配置，为缺失条目应用默认值，再依据应用提供的运行时依赖进行校验并构造运行框架。构造完成后，还可以选择发出带有 `source: "restore"` 的更新事件。

对于已启用工具：

- `active_tools_change` 条目是分支作用域内的持久化配置。
- 如果分支上没有 `active_tools_change`，恢复时使用构建器默认值；如果也未提供默认启用的工具名称，则使用所有已注册工具。
- 已启用工具的名称必须唯一。
- 工具注册表中的名称必须唯一。
- 如果恢复出的已启用工具名称不存在，默认应使恢复失败；以后可以显式增加较宽松的丢弃/禁用策略。
- 绝不从会话中恢复具体工具；宿主应用必须提供兼容的工具。

## 运行框架应持久化的内容

实现基本持久化能力至少需要以下条目：

- 分支作用域内的已启用工具名称
- 已排队的 `steer`、`followUp`、`nextTurn` 消息
- 与某一轮对话绑定的队列消费记录
- 活动操作期间已接受、尚待写入的会话数据
- 待处理写入的应用状态
- 操作开始/完成/中断
- 对话轮次开始/完成
- 服务提供商请求开始/完成（如果恢复诊断需要）
- 工具调用开始/完成（如果需要安全地恢复工具）

可能的条目类型：

```ts
type DurableHarnessEntry =
  | QueueEnqueuedEntry
  | QueueConsumedEntry
  | PendingWriteEnqueuedEntry
  | PendingWriteAppliedEntry
  | OperationStartedEntry
  | OperationFinishedEntry
  | OperationInterruptedEntry
  | TurnStartedEntry
  | TurnFinishedEntry
  | ProviderRequestStartedEntry
  | ProviderRequestFinishedEntry
  | ToolCallStartedEntry
  | ToolCallFinishedEntry;
```

公开 API 返回成功之前，每项已接受的变更都必须完成持久化。

## 恢复模型

启动时：

1. 宿主应用注册工具、模型、扩展、资源、身份验证和钩子。
2. 运行框架打开会话。
3. 运行框架归并会话条目，得到：
   - 当前叶节点
   - 对话分支
   - 运行框架配置，包括已启用工具名称
   - 队列
   - 待处理写入
   - 当前操作/轮次/工具状态
4. 运行框架校验所需的运行时依赖，包括对照应用提供的工具注册表，校验恢复出的已启用工具名称。
5. 运行框架协调未完成操作的状态。

服务提供商的数据流无法续传。恢复时只能从持久化边界重试，或者将操作标记为已中断。

## 恢复策略

默认采用保守策略：

- 未完成的智能体轮次：标记为已中断，保留持久化队列和待处理写入，回到空闲状态
- 未完成的服务提供商请求：标记为已中断，不自动重试
- 未完成的工具调用：追加中断/错误工具结果；只有工具声明可安全重试或具备幂等性时才重试
- 未完成的上下文压缩：如果不存在压缩条目，则重新执行
- 未完成的分支摘要/树导航：在安全的情况下重新执行，或补写缺失的摘要或叶节点条目

可选策略：

```ts
recovery: "mark_interrupted" | "retry_unfinished"
```

对于非幂等的工具调用，必须谨慎限制 `retry_unfinished`。

## 关键场景

### 队列

- 在写入 `queue_enqueued` 前崩溃：消息尚未被接受。
- 在写入 `queue_enqueued` 后崩溃：消息可被恢复。
- 队列取空后、对话轮次记录持久化前崩溃：存在消息丢失或重复的风险。
- 必须保持的不变量：只有先在 `turn_started` 或等效条目中记录已消费的队列 ID，才能将对应消息视为已消费。

### 待处理写入

- 在写入 `pending_write_enqueued` 前崩溃：该写入尚未被接受。
- 入队后、应用前崩溃：恢复过程会应用该写入。
- 应用后、写入已应用标记前崩溃：确定性的目标条目 ID 可让恢复过程发现条目已经存在，并将该写入标记为已应用。

### 智能体循环轮次

- 在服务提供商请求前崩溃：重试或标记为已中断。
- 在服务提供商请求期间崩溃：默认标记为已中断。
- 收到服务提供商响应后、助手消息持久化前崩溃：除非已将服务提供商结果写入日志，否则响应会丢失。
- 助手消息持久化后崩溃：从持久化消息恢复。

### 工具调用

- 工具调用开始后、返回结果前崩溃：外部副作用可能已经发生。
- 默认恢复策略不应重新运行非幂等工具。
- 若要自动恢复，工具调用需要稳定的 ID 和重试安全性元数据。

### 上下文压缩

- 生成摘要前崩溃：重新执行准备/摘要流程。
- 生成摘要后、写入压缩条目前崩溃：除非已将摘要写入日志，否则重新执行。
- 写入压缩条目后崩溃：操作已经完成；如果缺少完成标记，则追加该标记。

### 分支摘要/树导航

- 生成摘要前崩溃：重新执行或标记为已中断。
- 写入摘要条目后、叶节点条目前崩溃：补写缺失的叶节点条目。
- 写入叶节点条目后崩溃：操作已经完成；如果缺少完成标记，则追加该标记。

## 最小可行原型

1. 增加持久化队列条目。
2. 增加带有确定性目标 ID 的持久化待处理写入条目。
3. 增加操作开始/完成/中断条目。
4. 增加包含已消费队列 ID 的轮次开始条目。
5. 通过归并会话日志进行恢复。
6. 默认将未完成的智能体轮次标记为已中断。
7. 仅当最终条目不存在时，才重新执行未完成的上下文压缩/树操作。
8. 除非工具元数据声明可安全重试，否则不重试未完成的工具调用。

## 待讨论问题

- 剩余的运行框架配置中，哪些应优先移入会话：资源、流式传输选项，还是系统提示词引用？
- 是否应在每轮对话中保存解析后的系统提示词文本快照，以便审计和调试？
- 恢复时是否要求严格匹配依赖的 ID/版本？
- 应将多少服务提供商请求数据写入日志？
- 恢复过程应追加用户可见的助手中断消息，还是只追加内部操作条目？
- 存储层是否应支持在恢复时截断末尾不完整的 JSONL 行？
